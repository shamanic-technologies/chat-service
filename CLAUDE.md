## Regression Tests (MANDATORY)

**Every PR that fixes a bug or adds functionality must include tests.** This is a hard rule.

- **Bug fixes**: Add a test that reproduces the bug and verifies the fix. The test must fail without the fix and pass with it.
- **New features**: Add unit tests covering the happy path and key edge cases.
- **Test location**: `tests/unit/` for pure logic, `tests/integration/` for endpoint/DB behavior.
- **Naming**: Test file should mirror the source file (e.g., `src/lib/gemini.ts` → `tests/unit/gemini.test.ts`).
- **Minimum**: At least one new or modified test file per PR that touches `src/`.

CI will warn if source files change without corresponding test changes. Do not skip this.

## Tracking headers — allowlist-driven forward, NEVER per-field, NEVER to a vendor

Inbound tracking headers (`x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`, `x-audience-id`) are extracted in `src/middleware/auth.ts:extractWorkflowTracking` into `res.locals.workflowTracking`, then turned into the downstream header map by the **single allowlist helper `buildTrackingHeaders(workflowTracking)`** (same file). Every endpoint uses that helper — do NOT re-introduce the old per-field `if (workflowTracking.x) trackingHeaders["x-x"] = …` blocks at each route (they drifted: a new header had to be added in ~5 places and got missed). Add a new tracking header in exactly TWO spots: `extractWorkflowTracking` (read) + `buildTrackingHeaders` (forward), plus the `TrackingHeaders` types in `runs-client.ts`/`key-client.ts` and the `traceEvent` header builder. runs-client/key-client forward the map **generically** (`Object.entries` loop), so once a key is in the map it flows to runs-service + key-service automatically.

**`x-audience-id`** = the priority audience campaign-service picks at the start of a campaign run; carried for **per-audience cost attribution** (runs-service does a flat `SUM(cost) GROUP BY COALESCE(runs_costs.audience_id, runs.audience_id)`, no hierarchy rollup — so every run AND every cost row must carry it itself). It is forwarded on `createRun` + `addRunCosts` and stamped on the `sessions` row (`audience_id` column). Optional — absent outside the campaign flow; omit, never throw.

**Egress guardrail (security): tracking headers go to INTERNAL services ONLY, never to a third-party vendor.** The Gemini/Anthropic provider clients (`gemini.ts`, `gemini-chat.ts`, `anthropic.ts`) build their own vendor headers and contain ZERO tracking-header keys — keep it that way. `buildTrackingHeaders` is the only forward path and its output is asserted to be a strict subset of the internal allowlist (`tests/unit/workflow-tracking.test.ts`). Never pass `trackingHeaders` into a provider SDK call. (Standard OTel/DoorDash egress hygiene: drop everything but the vendor's own auth at the external boundary.)

## CI builds its database from the migration journal, in a container it throws away

`.github/workflows/test-check.yml` runs integration tests against a `postgres:17` **service container** in the runner — one per run, reachable by nothing else, gone when the job ends. No Neon, no external project, no API key, no delete step. Do NOT point CI at a shared, staging or production database: per-run isolation is the property that job exists to give.

The schema is built with **`drizzle-kit migrate`** (journal replay), NOT `drizzle-kit push`. Two reasons, both load-bearing: `push` derives the schema from `schema.ts`, which is not how this repo's schema is authored (see the next section), and `push` **exits 0 after a statement it could not execute** — so a half-built database reads as a green step and the suite then fails somewhere unrelated. `migrate` exits 1. `tests/integration/schema-parity.test.ts` is the second guard: it asserts every table, column and index `schema.ts` declares is live, and names what is missing.

**Every index that exists in production must be declared in `schema.ts`.** They are two independent statements of the same schema and they drift silently — `sessions_org_brand_idx` was created by migration 0012, has been in production ever since, and was absent from `schema.ts` until the CI cutover surfaced it (a `db:push` would have read it as drift and dropped it). The parity test now fails on any such gap.

## Drizzle migrations are HAND-AUTHORED here — `db:generate` is corrupted, do NOT trust its output

`drizzle/meta/` snapshots stop at `0009`; migrations `0010`–onward were hand-authored without snapshot updates. So `npm run db:generate` diffs against a ~0009 snapshot and emits a BOGUS full migration that re-creates tables and **DROPS** existing columns (it tried to drop `messages.run_id`/`campaign_id`/… and re-add already-live `sessions`/`app_configs` columns). NEVER ship `db:generate` output. To add a column: hand-author `drizzle/NNNN_<name>.sql` with an **idempotent** statement (`ALTER TABLE … ADD COLUMN IF NOT EXISTS …`) and add the matching `_journal.json` entry by hand (the runtime migrator keys on the journal `when` only; the snapshot JSON is not validated at runtime). Reference: `0015_add_audience_id_to_sessions.sql`.

## Direct vendor models (`deepseek` / `zai` / `moonshot`) — a THIRD path, never a replacement

`src/lib/openai-compatible.ts` is ONE OpenAI-compatible client parameterised per vendor, wired into `/complete` + `/internal/platform-complete` ONLY. It replaced the Vercel AI Gateway (removed 2026-08-15, v0.51.0 — the gateway resold these models 1.4x–4x above vendor list price). It exists so reaching a new model is a `MODEL_MAP` entry instead of a fourth hand-written native client. **Do NOT remove or degrade the Anthropic/Google native paths to "consolidate" onto it** — they carry vendor features these paths deliberately do not serve (thought signatures, the two mirror-image schema normalizers, per-generation thinking config, grounding, vision). **Do NOT write a second vendor client** — the three things that differ per vendor (base URL, key-service slug, cached-token field) are DATA in the `VENDORS` registry; a fourth vendor is a `VENDORS` entry, not a file.

**Concurrency is part of the model choice and is recorded next to the price (`VENDORS[...].concurrency`) — a swap justified on price ALONE is not justified.** Every vendor caps requests IN FLIGHT, and the cap does NOT track the price: Z.ai listed GLM-5.1/5.2/5.3 at the identical $1.4/$4.4 per 1M while serving **10 / 10 / 1** concurrent requests. `glm-pro` was repointed 5.2→5.3 on 2026-08-20 as a "drop-in swap, no contract change" on that identical price; it divided our throughput by ten, and three cold-email workflows sharing the one slot produced 127 rate-limit refusals in five hours and killed about half their runs (a run reaches the LLM only after paying for lead enrichment, so ~2/3 of that spend bought no email). **The concurrency table is a DATED SNAPSHOT, not a property of the model — Z.ai moves these numbers, so re-read the console before concluding anything from a value here.** On 2026-08-31 it raised 5.3 to **15** and published GLM-5.3-Flash at **50**; `glm-pro` resolves to **`glm-5.3`** again, this time checked on all three axes the first swap collapsed into one (price identical, concurrency 12/12 live, reasoning controllable — see the `perModel` note below). The rule that stands is not "5.3 is bad", it is that **a swap justified on ONE axis is unjustified**: price, published concurrency AND the reasoning control each get re-measured against the live API before an alias moves. DeepSeek publishes per model (v4-pro 500, v4-flash 2500, free expansion); Moonshot publishes per ACCOUNT TIER (Tier 0 = 1 slot, Tier 1 = 50 …), so a Kimi alias swap cannot change throughput but a balance drop can. `publishedConcurrency()` returns **null** where a vendor publishes nothing (`glm-4.7-flashx`) — never infer a number from a sibling model. **`glm-flash` moved `glm-4.7-flashx`→`glm-5.3-flash` on 2026-08-31 and that one is a deliberate PRICE INCREASE** ($0.07/$0.01/$0.40 → $0.15/$0.03/$0.50 per 1M), bought against 50 published slots (vs none published for flashx), two generations of model, and an exit from a model Z.ai has dropped from its `/models` listing (it still serves — probed 2026-08-31 — so this was pre-emptive, not a repair). `tests/unit/openai-compatible.test.ts` walks every alias and fails the build if one resolves to a model published at a single slot.

**Both DeepSeek aliases resolve to V4.1 Flash (`deepseek-flash`) since 2026-09-10, and the way that happened is the reason `assertModelMatches` exists.** DeepSeek released V4.1 Flash and renamed the Flash model id in the same move: `deepseek-v4-flash` left the `/v1/models` listing while still ACCEPTING requests and answering `model: "deepseek-flash"`. Nothing 400'd — the vendor simply served a different model under the old name, which is a different price under a cost name that no longer describes the spend. The guard refused it, so the alias 502'd from 04:00 UTC that day (instantly-service's reply classification and warmup messages were the live callers) instead of silently billing V4 Flash rates for a V4.1 Flash answer. **Never soften that guard to "recover" from a case like this** — a loud outage on a rename is the cheap failure; the expensive one is a quiet mis-declared cost nobody reconciles. The V4 Pro half was the same substitution on a four-day fuse (discontinued 2026-09-14T04:00Z, routed to V4.1 Flash at the Flash price), so `deepseek-pro` was repointed at the same time and kept as a DEPRECATED SYNONYM — deleting an alias is a breaking request-contract change and apollo-service + content-generation-service both still send it. V4.1 Flash is a NEW model, not a re-price (peak cache-miss input $0.3/1M vs V4 Flash's $0.44/1M), so it needed its own six catalog rows before it could ship; the retired `deepseek-v4-flash` / `deepseek-v4-pro` prefixes stay priced so past spend keeps resolving and are never declared again (`SUPPORTED_MODELS` keeps mapping them too — an unknown id there falls back to the ANTHROPIC default rather than failing, so deleting a row silently re-attributes historical DeepSeek spend to `anthropic-sonnet-4.6`). **The wire id and the cost prefix DIFFER for this model and that is not a bug to fix**: DeepSeek dropped the version from the id (`deepseek-flash`) while costs-service kept it in the row name (`deepseek-v4.1-flash`) so the generation stays legible beside the frozen V4 rows. That is the general rule wearing its ugliest face — the costPrefix convention describes the SHAPE of a catalog name, it does NOT derive one, so read `costs-service/src/db/seed.ts` on `origin/main` and copy the string byte-equal rather than deriving it from the model id. All three capability axes were re-probed live rather than inherited from the previous model — `json_schema` still refused / `json_object` accepted, `thinking:{"type":"disabled"}` still the working field (311→0 reasoning chars), 2500 published concurrency — which is the standing rule for any alias move, not a courtesy.

**Model breadth is NOT catalog breadth.** chat-service reaches only aliases declared in `MODEL_MAP`, and `resolveModel` throws on anything else naming the accepted set. Every alias costs THREE costs-service catalog rows (`<costPrefix>-tokens-input`/`-tokens-output`/`-tokens-cached-input`) that must be live in PRODUCTION before the alias ships, or runs-service 422s and the call fails loud. Never "enumerate a vendor's catalog" — add one alias + its rows, deliberately. Cost names are seeded in **costs-service `src/db/seed.ts`** (`SEED_PROVIDERS_COSTS`, upserted at that service's boot); `PUT /v1/providers-costs/{name}` only adds a price point to a name that ALREADY exists, so a new name needs a costs-service PR, not an API call.

**A cost prefix is NOT yours to invent — read costs-service's `SEED_PROVIDERS_COSTS` on `origin/main` and copy the string byte-equal.** The catalog's convention is the vendor's model id prefixed with the vendor slug UNLESS the id already names the vendor: `deepseek-v4-flash` stays bare, `glm-5.2` becomes `zai-glm-5.2`. Deriving the prefix from the model id "because that's obviously the shape" produced four names the catalog did not carry (v0.51.0 → hotfixed v0.51.1); costs-service had already merged the real ones. `git -C ~/conductor/repos/costs-service grep 'name: "' origin/main -- src/db/seed.ts` costs 5 seconds and is the only source of truth — a merged costs-service PR is visible there long before a row is queryable in prod.

**Cost names carry the priced DIMENSIONS, and the dimensions differ per vendor — `src/lib/cost-names.ts` is the only place that builds them.** costs-service prices one row per dimension a vendor actually bills, and the three vendors do not agree: **DeepSeek** prices cache-hit input apart from a miss AND splits peak (01:00–04:00, 06:00–10:00 UTC, Monday–Friday) vs off-peak → `deepseek-v4-{flash,pro}-{peak,off-peak}-tokens-{input,cached-input,output}`; **Z.ai** prices the cache only, no regime; **Moonshot** prices the cache only, no regime (rows live in prod from costs-service v0.46.0). Each vendor states its own dimensions in its `VENDORS[...].pricing` entry and `buildLlmCostNames` reads them — **never assume every vendor carries every dimension** (a fabricated regime or cached name 422s; a missing one bills a hit at the miss rate). The regime is selected from the **UTC clock at declaration, never the date** — costs-service effective-dated both regimes with today's identical rate until 2026-08-16T16:00Z, so the catalog resolves the right price for when the cost was written. Windows are half-open `[start, end)`. **A regime schedule is HOURS AND DAYS — the vendor moves BOTH, so re-read its pricing page before trusting the windows alone.** DeepSeek exempted weekends from 2026-08-22T16:00Z (00:00 Beijing on Sunday 2026-08-23; "off-peak rates applying throughout the day on weekends (Saturdays and Sundays, Beijing Time)"), and until the fix shipped on 2026-08-25 chat-service kept declaring peak on weekend days while the vendor invoiced off-peak — a live 2x customer overbill that nothing detected, because nothing compares a declared cost name to the vendor's invoice. **Actual exposure was ~7 hours, on ONE Sunday (2026-08-23)** — derive it from the windows that actually elapsed, not from the elapsed days: an exemption that starts partway through a day does not cover that day's windows that have already passed, so Saturday 2026-08-22 carried NONE of it (both peak windows, 01:00–04:00 and 06:00–10:00 UTC, were over hours before 16:00Z), Sunday 2026-08-23 carried both (3h + 4h = 7h), and Monday 2026-08-24 / Tuesday 2026-08-25 are weekdays that were priced correctly. Left unfixed it would have run at ~14h/week (2 weekend days x 7h of peak windows) — that forward rate is the reason it mattered, not the size of what already leaked. The scope lives on `VENDORS[...].pricing.regime` as `peakDaysUtc` + `peakDaysFrom` (dated, so past instants still resolve to what was actually charged). The vendor states its weekend in BEIJING days and we select on the UTC weekday; the two agree ONLY because every peak window ends by 10:00 UTC, well before the Beijing day rolls over at 16:00 UTC — `selectPricingRegime` asserts that and throws `AmbiguousPricingRegimeError` rather than mispricing if a window ever crosses it. **Never widen the day scope or drop the assert to make a new window fit** — evaluate the day in the vendor's timezone instead. **ONE timestamp per request** for both the hold and the actual, so a call straddling a boundary cannot hold peak and bill off-peak. The four flat `deepseek-v4-{flash,pro}-tokens-{input,output}` names are SUPERSEDED and FROZEN — they still resolve, which is exactly why declaring them silently under-bills; never reintroduce them.

**Pricing rule — PEAK rate, and cache hits ARE billed at the cache rate.** The catalog carries the PEAK list price for the peak rows so cheap hours are margin, never shortfall (same rule as pricing Gemini post-promotion). Cached prompt tokens are NOT billed as misses: `/complete` declares `tokensInput − cached` under the resolved `-tokens-input` name and the cached count under `-tokens-cached-input`, omitting the cached row entirely when the count is zero (or when the vendor prices no cache dimension, in which case the whole prompt is billed at the one input rate — that is the vendor's own billing, not an approximation). This is the economic point of calling the vendors directly — the gateway billed implicit-cache tokens at full input price regardless of what the vendor charged ([vercel/ai#13907](https://github.com/vercel/ai/issues/13907)). Each vendor reports the count in a DIFFERENT place (`prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens` / `cached_tokens`), which is why `readCachedTokens` is per-vendor data — **never cross-read another vendor's field** (it would invent a discount the invoice does not carry), and never estimate a split the response didn't report.

**Never add routing knobs or a fallback to the request body.** No `models` fallback array, no `sort`, no provider `order`/`only`. The vendor would then be free to serve a DIFFERENT model than the alias we priced, and the cost row would name a model that didn't run. `assertModelMatches` enforces the other half — it throws when the response's `model` is not the requested one (a DATED build of it is accepted: our aliases are version-free by convention). **Do NOT "improve reliability" by adding a fallback model or vendor** beyond the out-of-credit detour below (the one detour declares the model that ran under its own cost names and says so in the response); any other fallback trades a loud failure for a silently mis-declared cost.

**Retry connect-phase and a RATE LIMIT — nothing else.** A thrown fetch rejection with a transient socket cause is replayable (the request never reached the server): 3 retries, 250/500/1000ms. A `429` is ALSO replayable and must be replayed: the vendor turned the request away at its front door, so no model ran and nothing was billed, while the run that made the call has ALREADY paid for its upstream work (lead enrichment and the rest) — dropping the completion throws that spend away for a refusal that clears in a second. 4 retries, 500/1500/3500/7500ms, jittered ±25% (the requests that collide are the ones that started together, so an unjittered schedule marches them back into the same contended slot), honouring `Retry-After` up to 10s. **Never retry a completed 5xx** — a real answer that may already have been billed. **Never retry an out-of-credit 429** (Z.ai body code `1113`, Moonshot type `exceeded_current_quota_error`): an empty balance does not clear by waiting, so the retry would burn the budget on a certainty and delay the alert. **Never retry a 400/422** (`VendorUnsupportedOptionError`) — the same shape is refused forever. **Retrying must not HIDE saturation:** after the budget, `VendorRateLimitError` carries the attempt count, the total backoff and the model's published concurrency, and both completion routes answer **429** `{retryable: true}` rather than folding it into the generic 502. ONE schedule for all three vendors — a 429 means the same thing everywhere; per-vendor curves would be three numbers to keep true instead of one. Still deliberately narrower than `gemini.ts`'s 429/5xx retry; do not "align" them.

**Out of credit is a stored FACT, red on Monitoring, with ONE declared detour (VENDOR-CREDIT-1030, owner 2026-10-30; replaced the staff email, owner rule « red on Monitoring, never an email »).** `completeWithVendor` throws `VendorOutOfCreditError` when the vendor refuses in ITS out-of-credit words (`VENDORS[...].isOutOfCreditRefusal`; Anthropic/Google wording in `vendor-credit.ts:isOutOfCreditError`); both completion routes then (platform key only: an org's own key is the org's account) store the refusal (`vendor_credit_outages`, one OPEN row per provider via a partial unique index, + `vendor_credit_days`), and retry ONCE on `FALLBACK_MODELS` (`deepseek-flash` → `glm-flash` = GLM-5.3 Flash, same `cheap` tier, cheapest served model taking `responseFormat:"json"` without a schema; Haiku 5.5 is cheaper but Anthropic 400s that shape; never Haiku 4.5). The retry opens its own run and declares the FALLBACK's cost names, the response carries `fallback: {from, reason}`. While out, `pickServingModel` sends calls straight to the fallback and one call per `PROBE_INTERVAL_MS` (60s) to the primary; the first success closes the outage (`markProviderServing`). Open outages reload at boot. `GET /internal/vendor-credit?days=` serves verdict + sentence per provider and a day x provider series (api-service `/v1/chat/ops/vendor-credit`, dashboard v2 Monitoring). **Never key it on `429`** (Z.ai `1113` and Moonshot `exceeded_current_quota_error` share the rate-limit status; DeepSeek uses `402`); a rate limit, auth failure or bad request records nothing. A new fallback is a `FALLBACK_MODELS` entry after checking tier, price, request shape and that it serves in prod; never a request-body knob.

**Reasoning is OFF by default for STRUCTURED output on the direct vendors, and the field name is per-vendor DATA (`VENDORS[...].reasoning`).** Every model on these three vendors reasons before answering, the reasoning is billed as OUTPUT tokens, and neither completion route returns it — a `responseSchema` caller parses the object and never sees it. Measured in prod 2026-08-25: the same cold-email campaign at the same $24/day spent 316 output tokens per generation on Gemini and **9,633** on GLM, all of it reasoning nobody reads. So `buildVendorRequestBody` sends the vendor's reasoning-off field whenever the request asks for structured output (`responseSchema` or `responseFormat: "json"`); FREE-TEXT requests keep provider-normal behaviour, because that is the half where reasoning may shape the answer and no measurement says otherwise. `disableThinking` is TRI-STATE here — `false` keeps reasoning on for a structured request, `true` turns it off for a text one, omitted takes the default — and it is the SAME field the Gemini path exposes, not a second knob. The baseline for all three is `thinking: {"type":"disabled"}`; that is a fact about these three, NOT a rule — **never assume one vendor's field name carries**: DeepSeek and Z.ai answer **200** to an unknown top-level key and keep reasoning at full volume (probed with a junk key), `enable_thinking`/`reasoning_effort` are ignored by DeepSeek and Moonshot, and `reasoning_effort:"minimal"` made GLM-5.2 think MORE. A wrong name buys nothing and looks exactly like success. **The field name is ALSO per-MODEL, not just per-vendor — that is what `VENDORS[...].reasoning.perModel` is for.** Z.ai changed the spelling one model later: the whole GLM-5.3 family (5.3 AND 5.3-flash) hard-400s `thinking` with `code 1210 "This model always engages in thinking and cannot be disabled; please use low, high, or max"` and takes **`reasoning_effort`** instead, accepting `low|high|max` and nothing else (`"minimal"` draws the same 1210). Note this INVERTS one generation down, where `reasoning_effort:"minimal"` made GLM-5.2 reason harder — no value here transfers by family resemblance, probe the live API per model. A per-model entry REPLACES the vendor default rather than merging: sending both hands the model the field it refuses next to the one it accepts, and the refusal fails the whole request. Getting this wrong is not a cost regression, it is ZERO completions — unsent, GLM-5.3-Flash spent a whole 2,000-token cap on reasoning and returned a **zero-character answer**. **Never silently drop the field for a model that refuses EVERY spelling** — `refusedBy` is for that case (empty today; GLM-5.3 left it on 2026-08-31 when the working field name was found), the field is still sent, and the caller gets a 400 in the vendor's own words. A unit test fails the build if any alias resolves to a model listed in `refusedBy`. Measured cuts, same answers: glm-5.2 703→389 out tok, glm-4.7-flashx 1,036→329, kimi-k2.6 1,173→452 (its answer got LONGER), kimi-k3 543→360, deepseek-v4-pro 369→293. A fourth vendor declares `reasoning` after probing the LIVE API; the unit tests fail until it does.

**Structured output is PER VENDOR — read `VENDORS[...].structuredOutput`, never assume the json_schema form.** "OpenAI-compatible" is a claim about the request SHAPE, not about which values a vendor implements. DeepSeek accepts `response_format: {type:"json_object"}` ONLY and answers the `{type:"json_schema", json_schema:{schema}}` form `400 "This response_format type is unavailable now"` on both v4 models; Z.ai and Moonshot accept the schema form (all three probed live 2026-08-25). So a caller's `responseSchema` is sent as `json_schema` to a vendor that implements it and as that vendor's own `json_object` mode to one that does not — the caller still gets the model it asked for, and `parseModelJsonOutput` still fails loud (502) on unreadable output. **Never send a form a vendor refuses** — that is not stricter enforcement, it is zero completions (2026-08-25: 335 `deepseek-pro` calls, five hours, no successes, three campaigns spending and producing nothing; the alias had never been called in production so no request had ever carried a schema to DeepSeek). **A fourth vendor declares its value after PROBING THE LIVE API, not from the docs** — Z.ai's reference lists only `text`/`json_object` while its API accepts the schema form; `tests/unit/openai-compatible.test.ts` fails until the value is declared. Do NOT nudge the prompt to compensate (Prompt Ownership forbids it), and do NOT fall back to another model or vendor.

**A vendor refusing a request OPTION is a 400, not a 502 — `VendorUnsupportedOptionError`.** A vendor `400`/`422` means the request SHAPE was rejected: identical requests will be refused forever, so `"LLM call failed. Please try again."` is false advice and is exactly what let the incident above read as flakiness for hours. `completeWithVendor` throws `VendorUnsupportedOptionError` on those two statuses and both completion routes answer `400 {error, detail, retryable: false}` carrying the vendor's own message. Keep it NARROW: `401`, `402` (empty balance — rerouted when a fallback is declared, else 502), `404`, `429` and every `5xx` stay 502. This is the last line of defence, not the first — the capability data above is what stops us sending a refused option at all.

**OpenAI cache writes and long context are their own rows (LLM-HEADS-1027, 2026-10-27).** OpenAI bills cache WRITES at 1.25x input (`prompt_tokens_details.cache_write_tokens`, probed live) and a >272K-token prompt at 2x / 1.5x output for the WHOLE request; both were billed at plain input before. `VENDORS.openai.pricing` states `cacheWrite` + `longContextAboveInputTokens`, `vendorCostLines` builds the lines for every vendor. A vendor that prices no write (Moonshot) keeps it in fresh input. Catalog rows are always the FULL list price (Gemini 4 Argon declared at $4/$20, never its $2/$10 intro rate: a vendor discount is our margin, owner 2026-10-27). Kimi K3 / K3.1 Pro fix temperature at 0.6, so `moonshot` refuses sampling at the route.

**Text-only by design.** `webSearch` / `imageUrl` on these providers return 400 naming the vendor, rather than silently answering ungrounded or blind. (Kimi K3 does accept vision; wiring it needs per-vendor image encoding + its own cost story, so it is deliberately out of scope, not an oversight.) `/chat` is NOT wired to these providers and its config schemas (`AppConfigRequest`/`PlatformConfigRequest`) deliberately do NOT accept them — agentic tool-calling reliability on these models is unproven against our tool set and must be measured in a bake-off before any default moves.

**Removing or renaming a `provider`/`model` enum value is a BREAKING request-contract change — grep the sibling repos BEFORE shipping, not after.** These enums are a request contract other services code against; dropping a value 400s every caller still sending it, and the failure lands the moment prod deploys. `git -C ~/conductor/repos/<svc> grep -l '"<value>"' origin/main -- src` across the fleet is the check. v0.51.0 removed `provider: "vercel"` and broke content-generation-service, which mapped both DeepSeek aliases to that slug (fixed in ITS v0.30.1, after the fact). Adding a value is additive and safe; removing one is not.

## TypeSafe (`/orgs/judgments`) — a JUDGMENT vendor, and it does NOT belong behind `/complete`

`src/lib/typesafe.ts` reaches typesafe.ai, which answers a typed question with the model's own PROBABILITY DISTRIBUTION (`noul` = probability of yes, `choice` = winner + distribution + `confidence`, `score` = weighted position on ordered levels) and charges for INPUT TOKENS ONLY. Both halves are why it is a separate route and a separate client rather than a `MODEL_MAP` entry: `/complete`'s contract is prose out plus a two-sided token bill, so serving this vendor there would FLATTEN the answer to its winning value — throwing away the confidence that is the entire reason to adopt it — and declare an output cost the invoice does not carry.

**Never flatten an answer, and never serve one whose certainty went missing.** A consumer that FREEZES a classification at write time reads `confidence` to decide whether to freeze at all; an answer arriving without its `confidence`/`probabilities` is an ERROR here (502), not a degraded object passed onward — the distribution would otherwise read at the consumer as "not confident" or, worse, as absent. The route returns the vendor's answer objects verbatim.

**ONE cost name, `typesafe-jev-1.13-tokens-input` (copied byte-equal from costs-service `SEED_PROVIDERS_COSTS`), and it is the whole bill.** Output tokens are FREE at this vendor. Do NOT add an output row "for symmetry" with the LLM vendors — that bills a customer for something no invoice carries, the mirror image of the cache-miss overbill `cost-names.ts` exists to prevent. There is no cache dimension and no peak/off-peak schedule, so the vendor-driven resolver does not apply.

**The exact billable quantity comes BACK from the vendor, so the hold is never the charge.** The response reports `usage.input_tokens`. The pre-call reservation is a size estimate; after the call the route posts the REAL count as `actual` and releases the estimate-sized hold (a runs-service cost PATCH is status-only — no in-place quantity edit). A response without a usable `input_tokens` THROWS rather than letting us guess a charge.

**The wire always carries the pinned release `jev-1.13.0`, never an alias.** A caller may ask for `jev-latest` / `jev-preview` / `jev-1.13.0`; `TYPESAFE_API_MODEL_ID` is what is sent. The catalog name is keyed on the release, and the vendor ECHOES the id it was asked for — so forwarding an alias would bill a new model under the old release's name the day the alias moved, invisibly. A response served by any other id is refused (`TypeSafeModelMismatchError`), same doctrine as `assertModelMatches`: a loud outage on a rename is the cheap failure. A new Jev release is a deliberate edit, after its own catalog row is live in PROD.

**Retry the connect phase, a 429 and a 529 — nothing else, and never into silence.** Those two statuses are the vendor's own back-off advice and mean no model ran and nothing was billed, while the run has already paid for its upstream work. After the budget, the route answers **429** with `attempts` + `waitedMs` and `retryable: true` rather than folding saturation into a generic 502. A vendor 400/422 is a permanent refusal of the request SHAPE and surfaces as **400** carrying the vendor's words with `retryable: false`. The schedules and the transport predicate are SHARED with `openai-compatible.ts` on purpose — a 429 means the same thing at every vendor, so one schedule is one number to keep true instead of two.

**Images + a second judge (IMAGE-JUDGE-1021).** `image: {url}` is fetched and fitted ONCE (`judgment-image.ts`: longest side 1568, pad under 280, PNG) and every judge gets the same pixels, so a benchmark compares judges, not resizes. `judge` (`judges.ts`): `jev` default, `openai-luna` = OpenAI Decisions (`openai-decisions.ts`, own cost names, 2x row past 272K), `cloudflare-clef(-flash)` = Workers AI (`cloudflare-clef.ts`, same System One dialect as Jev, answers validated by the shared `parseTypeSafeAnswers`). Never a fallback between judges; never translate what Luna has no field for (score, noul criteria, choice examples → 400). A text-only Jev request stays byte-equal on the wire (pinned by `tests/unit/judges.test.ts`).

Every id needs a `MODEL_DISPLAY_NAMES` entry or the route throws.

**LLM dynasties (LLM-DYNASTY-1022, owner 2026-10-22): `MODEL_MAP` is keyed by DYNASTY SLUG, the old aliases are redirects.** `src/lib/llm-dynasties.ts` is the data: one dynasty = vendor line x tier, vendor's name, no version; thinking level and preview/GA stay in one dynasty; a renamed line joins only when the vendor says it REPLACES the old one; Flash and Flash-Lite are separate; Kimi K2 and K3 are two lines. Never remove a legacy alias (every workflow DAG names them). No `_` in slugs.

## Gemini `/chat` streaming — SSE framing must stay tolerant

`/chat` on `provider:"google"` streams via `gemini-chat.ts:streamGeminiChat`. Gemini's `:streamGenerateContent?alt=sse` stream frames events with **any of `\n\n`, `\r\r`, `\r\n\r\n`** and may emit `data:` with or without a trailing space — exactly what Google's official `@google/genai` SDK handles (`processStreamResponse`: `delimiters = ['\n\n', '\r\r', '\r\n\r\n']`, prefix `data:`). `parseGeminiSSEBuffer` mirrors this. **Never narrow it back to `indexOf("\n\n")` or `startsWith("data: ")`** — the real stream uses `\r\n\r\n`, so an `\n\n`-only parser yields ZERO events and an empty chat response with HTTP 200 and no error (incident 2026-06-01, fixed v0.32.2; the bug hid for the whole Anthropic-only period because the streaming parser had no test coverage). The Gemini stream path must also **fail loud**, not return `""`: throw on an in-band `{"error":...}` chunk and on a wholly-empty stream (no content, tool calls, or usage). When touching any provider's streaming parser, confirm the wire framing against that provider's official SDK source, not an assumption.

### Gemini 3 thought signatures — required on tool-call replay

Gemini 3 enforces [thought signatures](https://ai.google.dev/gemini-api/docs/thought-signatures): a `functionCall` part returned by the model carries an opaque `thoughtSignature` that **must be echoed back in the same part on every later request**, or the API returns `400 INVALID_ARGUMENT: Function call ... is missing a thought_signature`. (Gemini 2.5 only warns; Gemini 3 hard-400s.) `gemini-chat.ts` captures `part.thoughtSignature` from the stream, persists it on `ToolCallRecord.thoughtSignature` (jsonb), and re-attaches it on replay (`toGeminiHistory`) and in the agentic loop's `modelParts`. For tool calls recorded before the field existed (no stored signature), it injects Google's sanctioned bypass value **`skip_thought_signature_validator`**. **Never drop `thoughtSignature` from a replayed `functionCall` part** — every functionCall sent in history must carry one (real or the dummy), or multi-turn tool chats 400 on the second turn (incident 2026-06-01, fixed v0.32.3).

### Gemini 3 `functionResponse` — `$ref` in tool results must be sanitized

Gemini 3 reads `{"$ref": "<name>"}` inside a `functionResponse.response` as a reference to a **multimodal part** (the model substitutes the named part — see the [function-calling docs](https://ai.google.dev/gemini-api/docs/function-calling)). Tool results that embed JSON-Schema / OpenAPI `$ref`s — e.g. the api-registry / endpoint tools returning `{"$ref": "#/components/schemas/OrgId"}` — collide: the name matches no part `displayName`, so the API returns `400 INVALID_ARGUMENT: ... does not match to a display_name ...` and kills the chat turn. `sanitizeGeminiToolResponse` recursively renames every `$ref` key to `ref` (value preserved as plain data) and is applied to **both** the live tool result and the replayed result in `toGeminiHistory` (stored `tool_calls` carry the raw `$ref`). **Never send a tool result into `functionResponse.response` without this pass** (incident 2026-06-01, fixed v0.32.4). Only the `{"$ref": ...}` key form triggers it — a bare string containing `#/...` is harmless.

### Gemini tool DECLARATIONS — param schemas must be sanitized too (`sanitizeGeminiSchema`)

Gemini's `function_declarations[].parameters` is the **same restricted OpenAPI-3.0 `Schema` type as `responseSchema`** ([Schema ref](https://ai.google.dev/api/caching#Schema)) — it 400s on `additionalProperties`, `$ref`, `$schema`, `const`, `examples`, `exclusiveMinimum/Maximum`, `multipleOf`, etc. MCP tool input schemas (JSON-Schema 7) routinely carry these (a free-form/dict param emits `additionalProperties`; api-registry tools emit `$ref`), so `toGeminiFunctionDeclarations` (`gemini-chat.ts`) MUST run the built `parameters` object through **`sanitizeGeminiSchema`** (the same deny-list `/complete` uses for `responseSchema`, in `gemini.ts`) before sending. Symptom without it: `400 INVALID_ARGUMENT: Unknown name "additionalProperties" at 'tools[0].function_declarations[1].parameters.properties[0].value'` and the chat turn dies (incident 2026-06-06, fixed v0.35.3). **Never forward `t.input_schema.properties` raw into Gemini `parameters`** — the sibling sanitizer exists for exactly this OpenAPI-subset constraint; the tool-declaration path must use it just like the responseSchema path does. Supported keys the model needs (`type`, `description`, `enum`, `properties`, `required`, `items`, `nullable`, `format`, `pattern`, `minimum/maximum`, `anyOf`) survive the pass. Note the deny-list also drops `default`, which Gemini's Schema *does* support — harmless for tool params (the model loses only an optional default hint; the MCP server applies real defaults at execution), and not worth a second tool-only deny-list to preserve.

### Gemini billed tokens — declare `costLines` from `readGeminiBilledTokens`, never a `*TokenCount` field

Google bills one request along four dimensions and each is its own catalog name (costs-service seed): thinking (`thoughtsTokenCount`) at the OUTPUT rate beside the visible `candidatesTokenCount` (reading candidates alone under-declared ~75% of Pro output, Sept 2026); an implicit CACHE HIT (`cachedContentTokenCount`, a subset of the prompt, on by default) at 0.1x input → `-tokens-cached-input`; a Pro prompt over 200k tokens bills EVERY token of that request at `<prefix>-long-context-tokens-*`; Flash Image output splits into image tokens (`candidatesTokensDetails` IMAGE, `-tokens-output`, $60/1M) and text/thinking (`-tokens-text-output`, $3/1M). Gemini has NO fallback model (the 2.5 targets answer 404 since 2026-10; a retry-exhausted call fails loud). `src/lib/gemini-usage.ts` turns one response into those lines (`costLines`, keyed on `geminiCostPrefix(model)`, which throws on an unknown model), `/chat` sums them per turn, and every Gemini route declares `costLines` verbatim. It THROWS when `totalTokenCount` ≠ input + output, or on a cache hit for a model with no cache rate. A new Gemini model needs its `-tokens-cached-input` row (and long-context rows if Google tiers it) seeded in costs-service BEFORE it is routed. Anthropic (every route): `readAnthropicBilledTokens` sums compaction `usage.iterations` (top-level counts cover only the last sampling) into four dimensions and `anthropicCostLines` declares them (`-tokens-input` uncached, `-tokens-cached-input` reads, `-tokens-cache-write-5m` writes, `-tokens-output`). Prompt caching (5-minute, system breakpoint; `/chat` adds top-level auto-caching for the tail) is on ONLY for `ANTHROPIC_CACHE_PRICED_PREFIXES` (fable-5.1, sonnet-5.5, opus-5.5); a cache count on any other prefix or a 1-hour write THROWS. A new Anthropic model gets `cache_control` only after its cache-read AND cache-write rows are live in PROD. **Haiku 5.5 (`haiku` since 2026-10-09) is priced by PROMPT LENGTH** (>100k prompt tokens incl. cache read/write → every line under `<prefix>-long-context-*`, `ANTHROPIC_LONG_CONTEXT_THRESHOLDS`): the tier is picked PER REQUEST, so `/chat` merges per-request `anthropicCostLines` (`mergeCostLines`) — never sum `billed` across turns and price the total. Nothing routes to Haiku 4.5 (owner rule). DeepSeek, Z.ai, Moonshot, OpenAI `completion_tokens` and Anthropic `output_tokens` already include reasoning (checked live 2026-10-01).

### Gemini grounding cost — `webSearchQueries.length` is the CORRECT billed quantity (Gemini 3 bills per query)

Gemini 3 bills "Grounding with Google Search" **per executed search query**, NOT per request. Google's [grounding doc](https://ai.google.dev/gemini-api/docs/google-search) (verbatim): *"When you use Grounding with Google Search with Gemini 3, your project is billed for each search query that the model decides to execute … this counts as two billable uses of the tool for that request. This billing model only applies to Gemini 3 models; when you use search grounding with Gemini 2.5 or older, your project is billed per prompt."* So `/complete` actualizing the `google-search-query` cost as `groundingMetadata.webSearchQueries.length` (`src/index.ts` → `result.searchCount`) is **right** — a single grounded request fans out to ~12–20 internal searches and Google charges each. **Never "fix" this to qty=1-per-request** — that under-bills Gemini 3 grounding ~12× and we eat Google's real spend. (A real run flagged as a "~12× overbill" was genuine Google cost, not a bug — incident 2026-06-04, DIS-202; the per-request theory only holds for Gemini 2.5/older, which is not live traffic since the default `google/pro` = Pro 3.1.) The payload has **no** explicit "billed searches" field (`UsageMetadata` = token counts only; `GroundingMetadata` has no billing counter), so `webSearchQueries.length` is the only real-spend driver — it's already used at actualize. The pre-call `WORST_CASE_SEARCHES` hold (currently 20) is a reservation sized to the observed per-query max so platform-key AUTHORIZE doesn't under-reserve; it is reconciled to the actual count after the call and does NOT change the billed amount. The Anthropic path bills `usage.server_tool_use.web_search_requests` (per-request, correct for Anthropic) — do not unify the two. **Before treating any vendor cost as an "overbill" bug, WebFetch that vendor's billing doc and quote the per-unit metering model verbatim — assumptions about per-request vs per-query metering nearly shipped the wrong fix here.**

### Grounding search-count cap — Anthropic IS cappable (`max_uses`), Gemini is NOT

The number of grounding searches per request can only be bounded on **Anthropic**, not Gemini. The Anthropic `web_search_20250305` tool takes `max_uses` (`src/lib/anthropic.ts`), **pinned to 1** for cost control (each search = one billable `web_search_requests` unit at $10/1k). **Do NOT bump `max_uses` back above 1 without a cost review** — it directly multiplies grounded-`/complete` spend; `max_uses: 1` only truncates multi-entity comparison answers, single-fact lookups are unaffected. The native Gemini `googleSearch` tool exposes **no count-cap parameter at all** (verified against [Google's grounding doc](https://ai.google.dev/gemini-api/docs/google-search) — `GoogleSearch()` takes zero config fields; the model decides query count autonomously, ~12–20 fan-out, each billed on Gemini 3). **Do NOT try to add a Gemini search cap** — none exists in the API, and prompt-steering is not a hard cap (and `/complete` forwards the caller prompt byte-equal anyway). The deprecated `googleSearchRetrieval.dynamicThreshold` is a search-or-not gate, not a count cap, and is rejected by Gemini 3 models. A future `maxSearches` request param (DIS-211) will make the Anthropic cap caller-tunable; it will be a documented no-op for Gemini. (Shipped 2026-06-04, hotfix v0.35.1, DIS-213.)

### Gemini `/complete` — explicit `maxOutputTokens` (64k) is REQUIRED; never rely on the API default

`completeWithGemini` (`src/lib/gemini.ts`) MUST set `generationConfig.maxOutputTokens` (default `GEMINI_MAX_OUTPUT_TOKENS` = 64k, or the caller's `maxTokens` when supplied). This is **not** an artificial limit — Gemini falls back to a *lower* per-model **default** cap when the field is omitted, so omitting it gives the model LESS room and truncates long responses sooner. The Anthropic path mirrors it (`anthropic.ts` `MAX_TOKENS = 64_000`, lowered only by an explicit caller `maxTokens` — Anthropic's API *requires* `max_tokens`, which is why only the Gemini side ever silently lost its budget). **Never remove `maxOutputTokens` from the Gemini generationConfig "because the provider manages its own limits"** — that premise is backwards and is exactly what PR #140 did, regressing into truncated-JSON 502s (incident 2026-06-04). The pre-#140 code set it; it was correct. **This provider output CAP is a different number from the cost-provision HOLD — see the next section; do not re-couple them.**

When the model still stops at the budget (`finishReason: "MAX_TOKENS"`), the partial output in **JSON mode** is truncated JSON. `gemini.ts` **throws** `[gemini] Output truncated (MAX_TOKENS)` so the failure surfaces with a clear cause — NOT the cryptic `JSON.parse: Unterminated string` 502 that the downstream strict parse would otherwise emit. The throw decision keys on `jsonMode` (`responseFormat === "json" || responseSchema != null`), threaded into `callGeminiOnce` — do NOT narrow it to `responseFormat === "json"` alone, or `responseSchema`-only callers regress to the cryptic parse error. **Text mode** still returns partial content with a warning (preserves PR #132). This is fail-loud, not jsonrepair — it is consistent with the `/complete` strict-parse contract, not a violation of it.

### Gemini image generation — expose caller size; provision by image token estimate, never 32k

`/orgs/images/generate` and `/internal/platform-images/generate` accept `size?: "small"|"medium"|"large"|"xlarge"` and default to `small`. `generateImageWithGemini` maps this to `generationConfig.imageConfig.imageSize`: `small → "512"`, `medium → "1K"`, `large → "2K"`, `xlarge → "4K"`. Image generation does **not** send `maxOutputTokens`; size is the provider control.

Image output cost must use Gemini's documented image-token budget by size, not a model max: `small` 747, `medium` 1120, `large` 1120, `xlarge` 2000. The org route provisions/authorizes this estimate before the provider call, then reconciles to Gemini `usageMetadata.candidatesTokenCount` when present. The platform route has no provision/cancel, so if usage metadata is missing it posts the same size estimate as `actual` to avoid silent under-reporting. Do NOT restore the old `32_000` image output hold — that was a fake max, over-reserved credits, and did not represent provider image spend.

### Gemini THINKING must be bounded on `/complete` — `thinkingConfig: buildThinkingConfig(model)` is REQUIRED (Gemini 3 burns the whole budget thinking)

`completeWithGemini` MUST set `generationConfig.thinkingConfig = buildThinkingConfig(model)` (`src/lib/gemini.ts`). Gemini 3 thinking tokens count against `maxOutputTokens`, and a Gemini 3 model with NO thinkingConfig defaults to HIGH thinking, which can burn the output budget before emitting JSON (incident 2026-06-24, #316: brand-service ICP-suggest / human-service audiences-suggest / extract-fields). `buildThinkingConfig` is generation-specific: **Gemini 3.x (`gemini-3*`, incl `gemini-3.5-flash`) → `{ thinkingLevel: "low" }`; Gemini 2.5 → `{ thinkingBudget: 8192 }`.** It is the SAME helper the `/chat` path uses (`gemini-chat.ts`, commit 1991af2) — defined once in `gemini.ts`, imported by `gemini-chat.ts` (no circular import: gemini-chat already depends on gemini). **Never remove `thinkingConfig` from the `/complete` body** (that omission is the #316 bug), and **never "disable" Gemini-3 thinking with `thinkingBudget: 0`** (PR #133's value) — on Gemini 3 `thinkingBudget` is only accepted for backwards-compat and produces the same degenerate empty/truncated output; the disable knob for Gemini 3 is `thinkingLevel`, not `thinkingBudget`. This is a SEPARATE lever from the `maxOutputTokens` cap above — raising the cap alone never fixed the affected oversized extraction (thinking just consumed the larger budget too, exactly why #131's 16k→64k bump didn't help).

**`/complete` keeps the normal Gemini 3 bounded default unless the caller explicitly asks to minimize thinking.** Do NOT silently floor Gemini 3 thinking just because the request is on `/complete` or uses JSON mode. **Caller knob — `disableThinking` (POST /complete + /internal/platform-complete) is MODEL-FLOORED, never a guaranteed zero.** Callers can pass `disableThinking: true` to minimize thinking (extraction / JSON / scoring tasks). `buildThinkingConfig(model, disableThinking)` resolves it: **Gemini 2.5 → `thinkingBudget: 0` (fully off); Gemini 3 → the lowest level THAT MODEL accepts, read from the `GEMINI_3_THINKING_FLOOR` table in `src/lib/gemini.ts`; Anthropic → no-op** (the `/complete` Anthropic path never enables thinking — the `adaptive`/`clear_thinking` config is `/chat`-only).

The old code picked the floor from `startsWith("gemini-3")` plus `model.includes("pro")`, so the 2026-08-14 `flash-pro` → `gemini-3.7-flash` upgrade silently routed every `disableThinking: true` call to `minimal` → hard 400, 100% of the time, for 10 days (brand-service services-extraction + ICP-suggest, both dead on every new signup). **A model absent from `GEMINI_3_THINKING_FLOOR` THROWS** (`geminiThinkingFloor`) instead of guessing, and `tests/unit/gemini-thinking-floor.test.ts` walks `PROVIDER_MODELS.google` asserting every alias resolves to a model with a recorded floor — so the next alias upgrade fails a test, not production. Adding an alias means reading that model's row in Google's live table (and probing the API) and adding the floor; never inferring it. An EXPLICIT `thinkingLevel` below a model's floor also throws locally, naming the lowest accepted level — no silent swap to a different level. **Gemini 3 has NO full-off**, so document it as "minimize", exactly like the `maxSearches` cap (hard knob on one provider, best-effort on the other) — do NOT promise a literal zero on Gemini 3, and do NOT try `thinkingBudget: 0` on Gemini 3 (a backwards-compat no-op that re-degenerates the output). `/chat` does NOT expose the `disableThinking` knob — its agentic loop needs thinking for tool-calling.

**Caller knob — `effort` (POST /complete + /internal/platform-complete), Anthropic only (2026-10-12, brand-service on Opus medium).** Sends `thinking: {type:"adaptive"}` + `output_config.effort`; WITHOUT the `thinking` block these models do not reason on `/complete` (probed: 0 thinking tokens), so never send effort alone and call it reasoning. ### Cost provision HOLD is right-sized — decoupled from the provider output cap; never revert to a flat 64k

The pre-call cost reservation (`provision → authorize`) sizes the output-tokens HOLD via `resolveOutputBudget` (`src/lib/provision-estimate.ts`), NOT the flat 64k model max. The hold is the caller's `maxTokens` when declared, else a realistic estimate (`estimateOutputTokens`: prompt-size scaled, clamped `[1k, 8k]` tokens). The provider still receives the full 64k cap (or the caller's `maxTokens`) — the hold and the provider cap are TWO DIFFERENT NUMBERS. The hold is purely the affordability reservation; reconcile-to-actual records the true cost regardless, so an occasional larger output is billed correctly.

**Why this exists:** billing-service counts a `provisioned` hold as already-spent for affordability. A flat 64k hold (~115c) on EVERY call let a high-fan-out caller (human-service `/orgs/audiences/suggest` → ~12-25 concurrent `/complete` calls) stack dozens of maxed holds against one org balance in the same instant — 6 × 115c = 691c > a $5 credit → the balance read transiently NEGATIVE → false **402 "Insufficient credits"** on a solvent org, while real spend was ~0.15c/call (the hold was ~768× the real cost). Fixed by right-sizing the hold (PR #312).

**Never re-couple the hold to the provider's 64k cap** (the regression that caused the incident). The previous-section note that "64k matches the provisioned hold" was the OLD design and is gone. `/chat` uses the same right-sized hold (`estimateOutputTokens`); its streaming cap (`createStream` `MAX_TOKENS`) is separate and stays 64k. `/internal/platform-complete` posts actual-only (no hold), so it is unaffected. Integration tests in `tests/integration/complete-cost.test.ts` assert the hold quantity — they encode this invariant; if you change the sizing, update them deliberately, do not "fix" them back to 64k.

## Prompt Ownership — `/complete` family

**`/complete` and `/internal/platform-complete` MUST forward the caller's `systemPrompt` byte-equal to the provider.** No injection, no enrichment, no nudges. The caller owns the prompt end-to-end.

Concretely forbidden in these endpoints:
- Appending campaign / brand / workflow context fetched from another service
- Appending a "respond with JSON" suffix or any other behavior nudge
- Wrapping in any preamble or postamble

JSON mode is enforced **only** via native provider metadata:
- **Anthropic**: `output_config.format = { type: "json_schema", schema }`. Requires a `responseSchema` from the caller. Without it, return 400 — do not nudge via system prompt.
- **Gemini**: `generationConfig.responseMimeType: "application/json"` (+ optional `responseSchema`).

### Provider schema dialects are NORMALIZED, not delegated to the caller — and the two are MIRROR IMAGES, never unify them

The caller sends one JSON-Schema-7 / Zod `responseSchema`; each provider's structured-output API accepts a DIFFERENT restricted dialect, so chat-service normalizes per provider before forwarding. The two normalizers do OPPOSITE things and must stay separate:

- **Anthropic** (`prepareAnthropicSchema` in `src/lib/anthropic.ts`): strict mode REQUIRES every `type:"object"` node to carry an explicit `additionalProperties: false`. A permissive schema 400s with `output_config.format.schema: For 'object' type, 'additionalProperties' must be explicitly set to false` and — with no fallback parsing — kills the turn. `prepareAnthropicSchema` recursively STAMPS `additionalProperties:false` onto every object node (walking `properties`, `items`, `anyOf`/`allOf`/`oneOf`, `$defs`/`definitions`), preserving an explicit value the caller set. **Never forward `options.responseSchema` raw into `output_config.format`** — it must pass through `prepareAnthropicSchema` first (incident 2026-06-18, fixed v0.38.4; the bug 400'd every Anthropic `/complete` with a Zod-shaped schema). The route still 400s when JSON mode is requested with NO `responseSchema` at all — normalization fixes the *shape*, not the *absence*.
- **Gemini** (`sanitizeGeminiSchema` in `src/lib/gemini.ts`): the OpenAPI-3.0 subset REJECTS `additionalProperties` (and `$ref`, `$schema`, `const`, etc.), so it STRIPS those keys.

**Do NOT "unify" the two into one shared sanitizer** — Anthropic needs `additionalProperties:false` PRESENT, Gemini needs it ABSENT; a single deny-list/allow-list cannot serve both. Adding the key for Gemini reintroduces the v0.23.x-class 400; stripping it for Anthropic reintroduces the v0.38.3 400. Keep `prepareAnthropicSchema` (add) and `sanitizeGeminiSchema` (strip) as distinct, provider-pinned passes.

**No fallback parsing.** `response.json` is populated by strict `JSON.parse(content)`. A parse failure means the provider violated its enforcement contract and surfaces as 502. Do not reintroduce `jsonrepair`, LLM-repair rounds, or any other recovery pipeline.

`/chat` is the only endpoint that may compose the system prompt (Campaign Context block, Additional Context block via `buildSystemPrompt`). Do not generalize that pattern back to `/complete`.

## Workflow Tools (mutations) — three-tool contract

The only workflow-mutation tools exposed to the LLM are:

- `create_workflow` → `POST /v1/workflows/create` — new dynasty from NL.
- `upgrade_workflow` → `POST /v1/workflows/upgrade` — regenerate within the same dynasty. **The discriminator vs fork is INTENT, not topology.** Use upgrade whenever you are fixing a bug or repairing incorrect / broken / non-functional behavior — **EVEN IF the fix changes the DAG topology (adds, removes, or rewires nodes/edges)** — or clarifying wrong/imprecise metadata. workflow-service applies a topology-changed `dag` as a NEW VERSION IN THE SAME DYNASTY (api-service `/v1/workflows/upgrade` accepts an optional `dag`, shipped api-service #479; workflow-service bumps version + deprecates predecessor). Example: a workflow that runs but passes the wrong URL into a node, fixed by adding a node to fetch the correct value, is an UPGRADE. Accepts either `description` (LLM regenerates the DAG) or `dag` (skips LLM and applies the supplied DAG verbatim — use for surgical patches, per the surgical-fix guidance in `anthropic.ts`). At least one of the two is required.
- `fork_workflow` → `PUT /v1/workflows/:id` with a full DAG — creates a new dynasty when the signature differs; same-signature submissions return `_action: "updated"` and are surfaced honestly to the model (not a bug). **Use ONLY to introduce NEW behavior / scope / intent / audience.** A structural/topology change does NOT by itself justify a fork. **NEVER call fork_workflow without explicit user confirmation** — a fork creates a new production dynasty and changes which workflow future campaigns run (effectively irreversible). If the user asked for an upgrade, never fork; if a change genuinely needs a fork, STOP and ask first.

Do NOT introduce a metadata-only update tool, a single-node-config tweak tool, or any "shortcut" mutation path. Every workflow change must commit to either `upgrade_workflow` (fixing a bug / repairing incorrect-or-broken behavior, topology change allowed / metadata clarification) or `fork_workflow` (NEW behavior/scope/intent/audience, user-confirmed). "Sneak a tweak under the rug" is not a category we support.

### Two unrelated `workflowSlug` namespaces — do NOT mass-rename

Chat-service has two completely independent uses of `workflowSlug`-shaped identifiers. They are unrelated, must not be unified, and a grep-then-rename refactor across both is the wrong move.

1. **Tracking / grouping** — `sessions.workflow_slug` column, `x-workflow-slug` request header (read in `src/middleware/auth.ts`), `workflowTracking.workflowSlug` propagated through trace events, and the `groupBy: "workflowSlug"` axis on features-service. This is the **versioned** slug (e.g. `cold-email-outreach-nova-v3`) — it identifies a specific workflow version for run-tracking and per-version analytics. It MUST stay versioned.
2. **Workflow-service upgrade body** — `UpgradeWorkflowBody.workflowDynastySlug` (in `src/lib/workflow-client.ts`) and the `workflowDynastySlug` property on the `upgrade_workflow` Anthropic tool (in `src/lib/anthropic.ts`). This is the **dynasty** slug (e.g. `cold-email-outreach-nova`, never `-v3`) — workflow-service resolves it to whichever version is currently active. It MUST stay dynasty-only.

Symptoms of conflating the two: upgrade calls fail 400 because the LLM sends a `-v3` slug; OR feature-stats grouping silently collapses all versions into one bucket because the dashboard switched to `workflowDynastySlug` everywhere. Keep the two field names distinct in tool defs, route handlers, and tests.

### Tool descriptions are the enforcement surface

The system prompt is owned by the calling app (stored in `app_configs.system_prompt` / `platform_configs.system_prompt`). For behavioral rules we want to enforce regardless of the calling app — e.g. "upgrade is bug-fix only, even if the user asks otherwise" — encode them in the tool description in `src/lib/anthropic.ts`, prefixed with `HARD RULE — DO NOT VIOLATE EVEN IF THE USER ASKS YOU TO:`. Tool descriptions bind the model more reliably than system prompts and survive app-level config drift.

### Tool-error surfacing — BOTH agentic loops must run failures through `formatToolError`

A tool-call failure must reach the model as a **parsed, structured** `{error, tool, suggestion}` so it can self-correct — NOT a raw client error string. This applies to BOTH agentic loops and they must stay in parity: the Anthropic loop (`src/index.ts` catch → `formatToolError`) and the Gemini loop (`src/lib/gemini-chat.ts` catch → `formatToolError`). Do NOT reintroduce a bare `{ error: rawMsg }` on the Gemini path — that regresses to handing the model an unparsed blob (incident 2026-07-03: `upgrade_workflow` with a `script` node missing `config.code` failed and the Gemini path passed the raw error through, unlike Anthropic).

`formatToolError` (`src/lib/tool-errors.ts`) must extract field-level detail from **two** validation dialects and through api-service's double-encoding: Zod `issues[].path/message` AND workflow-service DAG `details[].field/message`. api-service commonly wraps a downstream **400 as a 500** and stringifies the body as `{"error":"<json>"}` (sometimes nested twice) — `parseValidationErrors` peels the nested `.error` wrappers and checks the field-errors BEFORE the status branch, so the actionable message survives the 500 wrapper. When adding a new downstream that returns a different validation shape, extend `extractFieldErrors`, don't special-case at the call site.

## Anthropic `/chat` prompt cache: a stable prefix, the turn's context after the user (CHAT-COST-1101, owner 2026-11-01)

## Multi-turn tool history — never strip globally

The Anthropic + Gemini APIs are stateless: every request must include the full prior conversation. For agentic chats this means each turn must replay every prior `tool_use` block paired with its matching `tool_result` block (or `functionCall` + `functionResponse` for Gemini). Without this pairing, the model has no record of which tools were called or what they returned in prior turns and either re-fetches or hallucinates — a silent UX regression that users perceive as "the assistant forgot what we just looked up".

`src/lib/merge-messages.ts:rebuildAnthropicHistory` and `src/lib/gemini-chat.ts:toGeminiHistory` rebuild these pairs from the `messages.tool_calls` jsonb column. Both deliberately filter only the **specific** orphan case (`toolCalls` entries with no `result`, i.e. `request_user_input` which pauses the agentic loop). They do NOT strip all `tool_use` blocks globally.

**Forbidden patterns** that have shipped here before and broke multi-turn memory:

- Calling `stripToolUseBlocks` (or any equivalent filter) on the assistant history at load time. The function still exists for persist-time cleanup of the final agentic-loop iteration; do not extend it to the load path.
- Reducing `tool_calls` to a `tool_count` summary or dropping it from the rebuild input — that loses the args/result content the model needs.
- Adding a per-tool `excludeFromHistory` flag to suppress tools like `list_workflows` from replay. If the data is too large, lean on the Anthropic beta `clear_tool_uses_20250919` edit (already wired in `src/lib/anthropic.ts:createStream`) which auto-clears the oldest tool uses past 120k input tokens (cache-aware thresholds, see the CHAT-COST-1101 section). For Gemini, `trimGeminiHistoryToBudget` accounts for serialized `tool_calls` length and drops oldest messages at >100k.

**Thinking blocks are bound to their prefix**: compaction / trimming rewrites it, so `createStream` sends `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` + beta `thinking-binding-controls-2026-08-01`. Never remove it: without it a long Copilot chat 400s "bound to a different conversation" on the turn after compaction (prod 2026-10-10).

When a new Anthropic 400 ("tool_use ids were found without tool_result blocks") surfaces, **find the specific orphan** (which agentic-loop exit path produced a `tool_use` without a `result`?) and filter exactly that case in the rebuild path. Do not reach for a broad strip — that was the 2026-03-25 mistake, and it cost two months of degraded multi-turn UX before anyone noticed.
